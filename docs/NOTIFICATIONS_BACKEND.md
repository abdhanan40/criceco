# Notifications — migration 25 (M3 P1), the Flutter data layer (P2) and the inbox on server data (P3)

**Status (2026-11-22):**
- **Migration 25** (P1): committed in `45d06ca`, validated on a disposable PostgreSQL 17. **Not applied to production.**
- **Flutter data layer** (P2, `6da3583`) and **the inbox on server data** (P3): behind the `CRICECO_NOTIFICATIONS` switch, off by default. See [P2](#p2--the-flutter-data-layer) and [P3](#p3--the-inbox-on-server-data). Without the switch, Supabase builds still show notifications as "not available yet"; the demo inbox is unchanged.

## Purpose and scope
Migration 25 adds the server side of the in-app inbox:
- **One `notifications` table.** Every person reads only their own rows. Read state is stored on the server, per notification.
- **Notifications are generated by triggers** on the tables of migrations 11–24. No live function changes. The trusted scorer path of migration 24 notifies too.
- **An inbox API:** a page of notifications, the unread count, marking some or all read.
- **Club announcements stored on the server.** The server picks the recipients and notifies them; until now announcements never left the device.
- **Privacy on account deletion,** and the 90-day window.

Push (FCM), preferences and scheduled reminders are later phases (P4–P6). They will read this table, so it needs no change for them.

## Tables

### `notifications`
| Column | Rules |
|---|---|
| `id` | uuid primary key |
| `recipient_id` | the person; `ON DELETE CASCADE` (D11) |
| `inbox` | `player` or `club_owner`, the app's two roles |
| `type` | one of the 23 types below |
| `params` | JSON object of at most 2 KB, nulls stripped: club, opponent and person names, dates, selection, result |
| `club_id`, `match_id` | what the notification is about; `ON DELETE SET NULL` |
| `subject_id` | the request, offer, challenge or announcement. No foreign key, so it can outlive the thing; the app shows "no longer available" |
| `person_id` | the other person named in `params.person_name`; `ON DELETE SET NULL` |
| `dedupe_key` | unique per recipient: one notification per event and person |
| `created_at`, `read_at` | `read_at` is set once and never cleared |

A guard trigger makes rows immutable. The only changes allowed are:
- `read_at` set once;
- `club_id` and `match_id` cleared by their foreign keys;
- `person_id` cleared by its foreign key, which also removes `person_name` and sets `person_deleted: true` (D11).

### `club_announcements`
| Column | Rules |
|---|---|
| `title` | 1–60 characters, whitespace tidied |
| `message` | 1–280 characters |
| `audience` | `all`, `players` or `staff` |
| `created_by`, `created_at`, `recipient_count` | |

The table is `ON DELETE CASCADE` with its club.

### `notification_lineup_state` (internal)
It keeps the last selection each player was told about, per match: `playing` or `sub`.

`save_match_lineup` deletes and re-inserts a whole line-up. Without this table, every save would notify everyone again.

## Events
| Type | When (table) | Recipient → inbox | `params` |
|---|---|---|---|
| `join_request_received` | a request is created (`join_requests`) | club owner → `club_owner` | club_name, person_name |
| `join_request_approved` | pending → approved | applicant → `player` | club_name, role |
| `join_request_declined` | pending → rejected | applicant → `player` | club_name (never the owner's reason) |
| `removed_from_club` | active → removed (`club_members`), unless the member removed themselves | the member → `player` | club_name |
| `ownership_offered` | an offer is created (`club_ownership_transfers`) | the member offered the club → `player` | club_name, person_name, expires_at |
| `ownership_rejected` | pending → rejected | the owner → `club_owner` | club_name, person_name |
| `ownership_withdrawn` | pending → cancelled | the member → `player` | club_name, person_name |
| `ownership_accepted` | pending → accepted | the previous owner, now a member → `player` | club_name, person_name |
| `challenge_received` | a challenge is created (`match_challenges`) | challenged owner → `club_owner` | opponent_name, format, custom_overs, proposed_date, venue_name (no message text) |
| `challenge_accepted` / `challenge_declined` | pending → accepted or declined | challenger's owner → `club_owner` | the same; `match_id` once accepted |
| `schedule_proposed` | a new proposal (`matches.proposal_version` increases) | the other owner → `club_owner` | opponent_name, starts_at, venue_name, city, reschedule |
| `schedule_accepted` | the proposal is accepted | the proposer's owner → `club_owner` | opponent_name, starts_at, venue_name, city, reschedule |
| `schedule_declined` | the proposal is declined | the proposer's owner → `club_owner` | opponent_name, starts_at, venue_name, reschedule |
| `match_rescheduled` | a confirmed match's new schedule is agreed | the selected players of both clubs → `player`, or `club_owner` for a selected owner | club_name, opponent_name, selection, starts_at, venue_name, city, previous_starts_at |
| `match_cancelled` | → cancelled | the other club's owner → `club_owner`, plus the selected players of both clubs | opponent_name, starts_at (+ club_name, selection for players); never the reason |
| `lineup_selected` / `lineup_changed` / `lineup_dropped` | a player's final selection differs from the last notice (`match_lineup_players`, checked when the save commits) | that player → `player` | club_name, opponent_name, starts_at, venue_name, selection, previous_selection, leader (captain / vice_captain) |
| `result_published` | the first official version (`match_results` → confirmed) | both owners → `club_owner`; the other active members of both clubs → `player` | club_name, opponent_name, result (won / lost / tied / no_result / abandoned, from the recipient's side), version |
| `result_corrected` | a later official version | the same | the same |
| `player_of_match` | an official version names them, once per match and player | that player | club_name, opponent_name |
| `announcement` | `publish_club_announcement` | the audience's active members, except the author → `player` | club_name, title |

**What doesn't notify:**
- expired requests, offers and challenges (P6 can add reminders);
- a match completing (the result tells it);
- a captaincy change on its own;
- a member removed while selected, who hears of the removal only;
- a provisional or rejected result;
- anything that is refused.

**Ordering in a fan-out:** the owner is told first, so an owner who is also selected gets one notification, not two (the same dedupe key).

## Functions (signed in; `auth.uid()` decides whose rows)
| Function | Returns | Errors |
|---|---|---|
| `my_notifications(p_inbox, p_before default null, p_before_id default null, p_limit default 30)` | newest first: `notification_id, type, params, club_id, match_id, subject_id, created_at, read_at`. For the next page, pass the last row's `created_at` and `id`. Last 90 days only | `notification: not authenticated` (42501); `notification: invalid` (22023): unknown inbox, limit outside 1–100, half a cursor |
| `notification_unread_count(p_inbox)` | integer (last 90 days) | the same |
| `mark_notifications_read(p_ids uuid[])` | how many changed (own and unread only; others' ids are ignored); at most 200 | the same |
| `mark_all_notifications_read(p_inbox, p_up_to default null)` | how many changed. `p_up_to` is the newest `created_at` the app showed, so a notification arriving meanwhile stays unread | the same |
| `publish_club_announcement(p_club_id, p_title, p_message, p_audience)` | `announcement_id, recipient_count` | `announcement: not authenticated` / `not allowed` (42501); `invalid title` / `invalid message` / `invalid audience` (22023); `too many` (P0001, more than 20 per club in 24 hours) |
| `club_announcement(p_announcement_id)` | the announcement, for its club's owner (with `recipient_count`) and its recipients (even after they left) | `announcement: not found` (P0002) for anyone else |
| `club_announcement_list(p_club_id, p_limit default 50)` | the club's announcements, newest first, owner only | `not allowed` (42501); `invalid` (22023) |

**Audiences:**
- `players`: members with a cricket profile (`player_profiles`);
- `staff`: members without one;
- `all`: both.

This matches the app's `ClubMember.plays`.

## Security and privileges
**Tables:** Supabase's default grants are revoked on the three tables for `anon`, `authenticated` and `service_role`. Then:
- `authenticated` gets `SELECT` on `notifications` only, with RLS policy "notifications: select own" (`recipient_id = auth.uid()`). That is the same row set as the API, and what Realtime will use later.
- No role can insert, update or delete directly, `service_role` included.
- `club_announcements` and `notification_lineup_state` have RLS on, no policy and no grant.

**Functions:**
- The 7 API functions are `SECURITY DEFINER` with an empty `search_path`, callable by `authenticated` only.
- The 12 internal functions (the guard, `notification_add`, the name and result helpers, the fan-out and the 7 trigger functions) are not callable by `anon`, `authenticated` or `service_role`.

**What notifications never carry:**
- no free text written by a user, except an announcement's title (its message is read through `club_announcement`);
- no decline or cancel reasons;
- no phone numbers, addresses or other profile data, only display names as snapshots.

## Account deletion (D11)
- **The person's own notifications** are deleted with their profile.
- **In other people's notifications:**
  - `person_id` becomes NULL and the guard removes `person_name` (`person_deleted: true`, which the app shows as "Deleted player");
  - the club name and the event stay;
  - a deleted club or match only clears `club_id` or `match_id`.
- **A selected player whose account is deleted** leaves the line-up without anyone being told "dropped". Their line-up state goes with their membership.

## Concurrency safeguards
- **Line-up notices are compared at commit** (a deferred constraint trigger), with the state row locked. A save waits for an earlier save of the same line-up (the `match_lineups` row lock), so it is compared against the committed result.
- **Announcements:** the club row is locked `FOR UPDATE`, so the daily limit holds under parallel publishes.
- **"Mark all read"** only changes rows its statement can see. A notification being written at the same moment stays unread, and a notification is never read twice.
- **Fan-outs are idempotent:** the key `(recipient_id, dedupe_key)` is unique and inserts use `ON CONFLICT DO NOTHING`.

## Rollback
`supabase/rollback/20261122_rollback_notifications.sql` removes the 7 triggers, all functions and the three tables, and nothing else.
- It **refuses while any notification or announcement exists**, unless `set local criceco.rollback_notifications_exported = 'yes'` is set in the same transaction. Export the rows first.
- With `CRICECO_NOTIFICATIONS` off, the app never calls these functions, so leaving the schema in place is harmless. Prefer that to a rollback.

## Production (not done; each step needs its own approval)
1. Backup and preflight.
2. Apply migration 25 in one transaction with `lock_timeout`.
   - Adding the 7 triggers and the foreign keys briefly takes `SHARE ROW EXCLUSIVE` on `join_requests`, `club_members`, `club_ownership_transfers`, `match_challenges`, `matches`, `match_lineup_players`, `match_results`, `profiles` and `clubs`.
3. Run the post-check.
4. Later: an APK with `CRICECO_NOTIFICATIONS=true` (after P2–P3).

## Known limits
- **No push yet (P5).** People see new notifications when the app refreshes (D12).
- **No expiry or "match tomorrow" reminders** (P6: `pg_cron`). Expired requests, offers and challenges are silent.
- **No cleanup job for rows older than 90 days** (P6). They are hidden by the read functions.
- **Results fan out to every active member of both clubs.** With today's club sizes that is a few dozen rows per result.
- **A client cannot defer line-up notices to "immediate":** PostgREST does not expose `SET CONSTRAINTS`. Run by hand as the owner, it would send "dropped" and then "selected" for one save.

**Request rules:**
- **Paging:** a full page continues after its last row. The cursor keeps the server's exact timestamp text, because a parsed date can lose microseconds on the web and skip rows. The page size is 1–100.
- **`markRead`** sends unique ids only. With none, it makes no call. More than 200 ids go in batches of 200.
- **`markAllRead`** takes the cursor of the newest notification shown, so one arriving meanwhile stays unread.

## P3 — the inbox on server data
**With the switch** (Supabase + memberships + `CRICECO_NOTIFICATIONS`), `BackendModule.notifications` and `.announcements` become available. The bell, the panel, the Notifications screen and Create Announcement then work on the server.

**Without the switch,** nothing changes:
- Supabase builds still show "not available yet".
- The demo inbox works exactly as before, with session-only read state.
- No request is made (tested).

**Read state (D6):**
- **Opening a row** marks it read at once in the list and the badge, then on the server. A mark the server refuses is undone quietly, and opening still works.
- **"Mark all read"** covers everything up to the newest row shown, so one arriving meanwhile stays unread. Afterwards the count is fetched again from the server. If it fails, the list is restored and a toast says so.

**Refresh (D12):**
- The inbox refreshes on opening, on pull-down and on resume.
- A failed refresh keeps what was shown, with a toast on pull-down.
- Realtime is still for later.
